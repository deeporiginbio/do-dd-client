# Principles for designing Drug Discovery classes

## Scope

This concerns the tool/execution wrapper classes:

- Execution
- AsyncExecutionMixin
- SyncExecutionMixin
- Docking
- SystemPrep
- PocketFinder

etc

and the result/entity classes

- Entity
- Pocket
- Ligand
- LigandSet
- Protein
- PreparedSystem


## Principles

1. Sync operations should happen under `.run()`. Long running tasks that are async should be started using `start()`. 
2. `start()` should return None. `run()` returns the result object types as a convenience. Internally, `run()` calls `client.executions.create()` and then calls `get_results()` to retrieve results. 
3. No matter how we run a tool, the API to retrieve results should be the same -- `get_results()`. This should use the superclass method internally, and return a list or the object that that tool returns. e.g., Docking.get_results() should return LigandSet, SystemPrep.get_result() should return PreparedSystem, so on. 
4. `get_results()` should first verify that we have an execution ID. It should not require a terminal state, because some tools may expose partial results while running. Then it should try constructing output result types directly using their `from_result` method. For example, PocketFinder.get_results() should try `Pocket.from_result(execution_id=self.id)`. If that fails, or doesn't get any results, we should fall back on the output type's `from_json` method. Example, PocketFinder falls back on `Pocket.from_json(data)`, where data comes from `jobOutputs` of the DTO. If this fails too, raise a DeepOriginException. 
5. A corollary of this is that the entity/result classes need to implement both a `from_json` and a `from_result` method (for any entity that is generated by a sync tool). Every entity/result class must implement a `from_result` method. Perhaps we need a `Result` superclass that defines a `from_result` abstract method?
